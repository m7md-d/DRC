# Writing

Use short, factual sentences. State what an action does, what happened, and what the user can do next when that is known.

- Buttons name actions: **Inspect**, **Create image**, **Copy command**.
- Results name observations: **Device detected**, **Source access denied**, **12 unreadable sectors**.
- Errors retain the failed operation, original error code and useful context. Do not guess a hardware cause.
- Hints explain a control or a measurement. Do not repeat its label or fill space with reassurance.
- Keep risks that affect the user's decision at the relevant operation. Put technical background and test history in developer documentation.
- README: purpose, functions, installation, screenshots and links.
- Release notes: a short list of changes, plus installation or compatibility changes when relevant.

Avoid slogans such as “Your disk. Your next step.”; claims such as “powerful”, “seamless”, “ultimate”, “trusted” and “recover anything”; and openings such as “we're excited”, “unlock”, “empower” and “take control”. Describe the function instead.

Raw device names, vendor strings, command output and imported reports are source data. Do not rewrite them to match this style.
