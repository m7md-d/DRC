# SSD acquisition resilience: observations, cases and tested boundaries

The target is human-reported as **Samsung M.2, model MZ-9LQ256A, not working**, with filesystem text **NTSF** (likely intended as NTFS; not verified by a reader). Its serial is stored only in the ignored local target case, not this public research document. M.2 is a form factor, not sufficient evidence of SATA versus PCIe/NVMe. No manufacturer document matching this exact model was verified; PM991 and PM991a examples below are related cases, not an identification or diagnosis of this target.

The failed physical SSD is unavailable. Recovery tests use generated regular image files; none use the owner's personal flash. Real hardware, voltage/current, NAND access, controller reset and blocked kernel I/O remain separate validation work. DRC reports observations and lets the user decide; it does not rank causes or choose recovery actions automatically.

## Real cases and what DRC must preserve

| Observed situation | Published evidence | DRC behavior and limits |
| --- | --- | --- |
| No SSD in BIOS / OS after a firmware condition | HP documents some Samsung PM991 systems losing SSD detection after meta-block erase-count thresholds. | Preserve controller and host evidence, including when no block device exists. This does not establish that the target has this condition. HP's firmware update is described as prevention, not a proved recovery method for an already inaccessible source. No firmware update is run by DRC. |
| Controller disappears or fails after low-power transitions | A Linux NVMe maintainer documents APST / ASPM interactions for some controller/platform combinations. APST transitions are autonomous and are not necessarily logged individually. | Preserve kernel errors, controller state, current link properties and reported power configuration. Missing transition logs do not prove power was stable. DRC does not change APST, ASPM or boot parameters automatically. |
| USB enclosure exists but no usable storage namespace appears | USB topology and driver enumeration are distinct from a usable block device / NVMe namespace. | Host connection reports can be collected without selecting a disk. Linux Host evidence records PCIe and NVMe-controller sysfs attributes independently of lsblk. An enclosure identity is not proof that its attached SSD is readable. |
| Device supplies a readable prefix, then errors or ENODEV | Linux errors and ddrescue mapfile statuses distinguish failed reads from finished bytes. | Save the image/map pairing and exact output; preserve the completed ranges. A full-sized image can still be incomplete. Do not label process exit zero or zero bad-sector bytes as complete recovery. |
| Reads return fewer bytes than requested | A read can be short or reach EOF before the originally reviewed extent. | Record actual map coverage and keep the reviewed capacity. Test byte content against known generated data. Do not silently shrink the source or invent readable sectors. |
| A read is delayed, including after a stop request | ddrescue's successful-read timeout does not force the kernel to return an outstanding request. | Stop is a request; wait for actual exit and saved artifacts. The userspace delay test below demonstrates deferred handling, not a guarantee for uninterruptible kernel waits. |
| Capacity is zero, changes, or is smaller than the expected label | Device descriptors and reported capacity can be missing or change after an error/reconnect. | Refuse zero capacity, changed descriptors and unresolved sources. Completion concerns the reviewed requested domain and reported size, not a proved manufacturer capacity. |
| No controller response / no accessible logical sectors | The NVMe specification distinguishes controller initialization, readiness, error reporting and namespace access. | No imaging tool can copy LBAs that the interface does not expose. Host evidence remains useful. Controller/board/NAND access and measured power require hardware capabilities outside the software. |

Sources: [HP PM991 detection advisory](https://support.hp.com/us-en/document/ish_9955528-9955572-16), [Linux NVMe maintainer discussion](https://lists.infradead.org/pipermail/linux-nvme/2022-May/031961.html), [NVMe error/reporting overview](https://nvmexpress.org/resource/features-for-error-reporting-smart-log-pages-failures-and-management-capabilities-in-nvme-architectures/), [NVMe base specification 2.1](https://nvmexpress.org/wp-content/uploads/NVM-Express-Base-Specification-Revision-2.1-2024.08.05-Ratified.pdf), [Samsung M.2 / NVMe explanation](https://org-ap-publish.semiconductor.samsung.com/us/consumer-storage/support/faqs/internalssd-product-information/), [GNU ddrescue manual](https://www.gnu.org/software/ddrescue/manual/ddrescue_manual.html).

## Linux operations intended for serious acquisition

- On-request lsblk / udev descriptors, host topology, controller sysfs attributes and original kernel messages. These reports remain independent; DRC does not infer a connection between two observations solely from a model name.
- Acquisition from a resolved **non-system hardware disk**, including a secondary internal SATA or NVMe disk. System paths, active swap, mounted sources and unresolved backing are excluded. macOS keeps its separate external-source requirement.
- Exclusive read-only source opening, with a narrowly scoped UDisks2 OpenDevice request when direct access is denied. The returned descriptor must be read-only and match the block device; no app-wide root process is used. Physical authorization/exclusion needs testing on a dedicated test device.
- Explicit copying-only / full phases, bounded retry passes, rate cap, successful-read timeout and forward/reverse direction. No automated reset, firmware update, rescan, repeated reconnect or source write.
- Per-attempt logs, persistent mapfiles, strict artifact-bound resume and final image-size / requested-domain coverage verification. Rebinding a changed identifier and adopting newer crash artifacts remain unavailable; a strict refusal is not silently bypassed.
- All source/destination admission and protection rules apply equally in Easy and Professional. Images and mapfiles stay on a separate resolved destination; metadata-only media cannot be a destination.

## Fault test scope

The standard Rust suite runs real GNU ddrescue 1.30 against generated images, including simulated unreadable regions, controlled stop, same-image/map resume, altered artifacts and exact restored-byte comparison. Sleuth Kit tests exercise generated FAT16 / MBR filesystems with allocated, deleted, Unicode and fragmented binary files.

`scripts/linux/test-faults.py` compiles a **test-only** userspace read interceptor. Only an inherited descriptor referring to the generated regular source image is affected. Cases include short reads, ENODEV after a readable prefix, and a delayed read overlapping SIGINT. Each case preserves finished map regions, resumes the same pair in reverse after removing the injected fault, checks exact output bytes and verifies the source remained unchanged. This interceptor is not packaged or enabled in the application.

Host-evidence tests preserve a reported dead-controller state and non-UTF-8 attribute bytes without creating any block-device namespace. Backing tests resolve partitions and layered hardware stores, and reject virtual / cyclic / unresolved graphs. Broker-result tests reject writable and regular-file descriptors.

`scripts/linux/test-kernel-claim.py` tests actual Linux kernel semantics on an owned, generated 16 MiB read-only loop image in an isolated container. Mounting while its exclusive handle is held is refused; exclusive opening while mounted returns EBUSY; writing through the read-only descriptor returns EBADF; the source hash stays unchanged. The container receives loop control only for this test and no host disk or host directory. This validates the kernel claim mechanism, not the UDisks2 authorization flow or a physical SSD. The GitHub build runs this check separately on both architectures and publishes its scoped JSON evidence alongside the fault-test results.

These are software tests against controlled failure surfaces. They do not validate an actual damaged controller, lost NAND translation tables, firmware-specific recovery mode, real electrical instability, OS authentication UI, physical reconnect or a blocked kernel call. They also do not establish recoverability of the Samsung target.
