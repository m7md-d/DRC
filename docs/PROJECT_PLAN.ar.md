# خطة DRC

**التاريخ:** 13 أكتوبر 2026. **المرحلة:** تصميم قبل التنفيذ.

## 1. هدف المنتج

توفير مكان واحد يعرض القراءات ومعلومات الأقراص المتصلة كاملة، ويتيح للمستخدم اختيار الأدوات والعمليات ومعاملاتها من واجهة رسومية، مع الأمر الفعلي والمخرجات الأصلية. **الاستنتاج عن سبب العطل واختيار الإجراء وظيفة المستخدم، وليسا وظيفة DRC.**

القيمة الأساسية هي الوصول إلى المعلومات والمعاملات دون فقد تفاصيل الأدوات، وتحديد المصدر والوجهة، وحماية المصدر، وحفظ التقدم. المستخدم يختار العملية والأداة؛ المحرك يتحقق من دعمها ومن سياسات التنفيذ المحددة. لا توجد طبقة تشخيص آلي أو ترجيح أسباب أو اختيار خطوة تالية.

التنظيم والترجمة وفك ترميز الأعلام حسب الوثائق يضاف إلى القيمة الأصلية ولا يستبدلها. لا تختزل المخرجات في درجة صحة أو وصف عام. إذا أبلغت أداة أو جهاز عن حالة مثل SMART PASSED أو Critical Warning تعرض كما أبلغها المصدر، مع اسمه وحقوله الأصلية، ولا تحول إلى حكم من DRC على سلامة القرص.

## 2. الحالة الحالية ومتطلبات المستخدم

- مشروع فارغ عند بدء التخطيط؛ لا توجد هيكلة أو مستودع Git قائم في المجلد.
- الجهاز الحالي: Mac M1 وفق المستخدم؛ النظام المتحقق منه محليًا macOS 15.7.9، arm64.
- smartctl 7.5 مثبت؛ وثيقته المحلية تذكر أن Darwin SCSI غير منفذ، وأن USB SAT يعتمد على دعم إضافي. لذلك لا نفترض أن خيارات جسور USB المتاحة على Linux متاحة على هذا الجهاز.
- **تحديث 14 أكتوبر 2026:** الـSSD المعطوب لم يعد متاحًا وفق المستخدم. نتابع التنفيذ والاختبارات على صور ملفات أنشأناها؛ لا نطلب إعادة توصيله. العرض الذي أبلغ عنه المستخدم كان الفصل والعودة تلقائيًا، وهو ملاحظة مستخدم وليس تشخيصًا من DRC.
- **الأولوية المعتمدة: إنقاذ البيانات قبل محاولة إصلاح القرص أو إعادته للاستخدام.**
- فلاش شخصي سليم سيستخدم للكشف وعرض المعلومات فقط؛ له سياسة مستقلة تمنع العمليات الأخرى.
- واجهة إنجليزية بالكامل للمستخدم المحترف، مع المصطلحات الأصلية والوحدات والقيم الخام كاملة؛ التنظيم لا يمنح حق حذف أو تبسيط المخرجات. لغة هذه الوثيقة لا تحدد لغة المنتج.
- البرنامج لا يستنتج سبب العطل، ولا يعرض احتمالات أو درجة ثقة أو إجراءً مقترحًا. يتيح جمع المعلومات واختيار العمليات للمستخدم.
- أقراص ويندوز ضمن الاستخدام الأساسي حتى أثناء تشغيل DRC على الماك. NTFS وexFAT وFAT لها أولوية في التعريف وتحليل الصور واستخراج الملفات؛ الهيكلة لا تفترض APFS أو أي نظام ملفات واحد.

لم يتم جمع قائمة الأقراص أو تشغيل فحص عليها خلال هذه المرحلة. القراءة المحلية اقتصرت على معلومات النظام ووثائق الأوامر ونسخة الأداة المثبتة.

## 3. اسم المنتج

**DRC — Disk Resource Console**. النطاق هو الأقراص ومحتواها: الفحص والنسخ والاستعادة، مع تحليل المساحات ومحتوى صور الأقراص ضمن التوسع المستقبلي. مراقبة الجهاز ميزة مساندة.

## 4. مدى ملاءمة Mac M1

| المهمة | التقييم العملي |
| --- | --- |
| رصد الأقراص وربطها بمسار التوصيل والأقسام | مناسب عبر Disk Arbitration وIOKit وdiskutil |
| تصوير أقراص ويندوز أو أي نظام ملفات | النسخ الخام مستقل عن نوع نظام الملفات طالما يوفر الجهاز قطاعات قابلة للقراءة |
| تحليل NTFS وexFAT وFAT واستخراج ملفاتها | عبر قارئات أنظمة ملفات/أدوات تحليل صور مناسبة، دون اشتراط أن يركبها macOS |
| التعامل مع APFS وHFS+ وصور الأقراص | مناسب عبر أدوات النظام، مع حدود للتلف والتشفير |
| إنشاء صورة قطاعات لقرص يستجيب | مناسب عبر GNU ddrescue، واختبار مسار rdisk على الجهاز الفعلي |
| SMART لأقراص خارجية | مشروط بالنظام والمحوّل وتمرير الأوامر؛ ظهور القرص لا يضمن ظهور SMART |
| أوامر NVMe/SATA المتقدمة والتحكم بالمهل وإعادة الضبط | Linux على جهاز ذي اتصال مباشر يتيح خيارات أوسع؛ ليس ضمانًا للإنقاذ |
| قياس الأمبير/الفولت الفعلي | ليس قدرة عامة للنظام؛ يحتاج جهاز قياس يدعم توصيل البيانات المستخدم |
| إنقاذ NAND أو متحكم لا يقدم قطاعات | خارج حدود أدوات النسخ العادية؛ قد يتطلب معدات ومختصًا مناسبًا للموديل |

Apple توفر إشعارات ظهور الأقراص واختفائها والمشاركة في قرار التركيب عبر [Disk Arbitration](https://developer.apple.com/library/archive/documentation/DriversKernelHardware/Conceptual/DiskArbitrationProgGuide/Introduction/Introduction.html). محرك [nvme-cli](https://github.com/linux-nvme/nvme-cli) مثال للقدرات المتقدمة في بيئة Linux. استخدام VM لا يمنح تلقائيًا وصول PCIe مباشرًا أو يتجاوز حدود محول USB.

نستهدف أن يعمل التطبيق على macOS وWindows وLinux. دعم نظام آخر يعني إضافة وحدة واختبارها؛ ليس وعدًا بتطابق جميع القدرات على أي نظام.

### فصل نظام المضيف عن محتوى القرص

ثلاث قدرات مستقلة في المنتج:

1. **الوصول للجهاز:** خاص بـmacOS/Windows/Linux وبمسار التوصيل.
2. **القراءة والنسخ الخام:** يعمل على القطاعات والنطاقات دون الاعتماد على نظام الملفات، ويشمل وسيطًا مشفرًا أو مجهول البنية دون ادعاء فتح محتواه.
3. **قراءة الملفات واستعادتها والتحقق/الإصلاح/التهيئة:** قدرات لكل نظام ملفات ولكل backend وإصدار؛ لا تتطلب دائمًا تركيب القرص في نظام المضيف.

توجد وحدات مستقلة للبنية والتشفير والحاويات. تعرض مصفوفة كل نظام ملفات: التعرف، وعرض metadata، وتصفح الملفات، واستخراجها، واستعادة المحذوف، والتحقق، والإصلاح، والتهيئة. دعم واحدة لا يفترض دعم البقية. BitLocker طبقة تشفير تحتاج مفتاحًا وbackend مناسبًا للوصول إلى الملفات، وليس نظام ملفات بديلًا عن NTFS. ReFS وحاويات Windows مثل Dynamic Disks وStorage Spaces حالات توسعة مستقلة تختبر قدراتها قبل إعلانها.

تعلن [Sleuth Kit](https://www.sleuthkit.org/sleuthkit/desc.php) دعم أنظمة بينها NTFS وFAT وexFAT مستقلًا عن نظام المضيف. وتوضح [Microsoft](https://learn.microsoft.com/en-us/windows/security/operating-system-security/data-protection/bitlocker/index) طبيعة BitLocker كتشفير؛ لا نخلط تصوير القطاع المشفر مع استخراج ملفات مفكوكة التشفير.

## 5. جلسة قياس SSD الحالي

المعلومة الحالية من المستخدم: SSD يفصل ويعود، والبيانات أولوية. يسجل البرنامج هذه الملاحظة ومعلومات التوصيل والقراءات؛ لا يولد احتمالات لسبب العطل ولا يقرر أنه خلل بورد أو طاقة أو متحكم.

أدوات الجلسة التي يختار المستخدم تشغيلها عند توفير القرص:

1. تسجيل الموديل والتوصيل والتاريخ المختصر وأهمية البيانات قبل توصيله للتجربة.
2. تجهيز وجهة سليمة وحماية المصدر قبل التوصيل متى أمكن، خصوصًا للبيانات الحساسة.
3. عرض جهاز USB ووسيط التخزين كلًا على حدة، مع السعة المبلغ عنها وتغيرها بين أحداث الاتصال.
4. جمع حدث الاتصال والفصل، وهوية المحول، وسرعة الرابط المعلنة. لا تبدأ قراءات عميقة تلقائيًا.
5. إتاحة قراءة حقول SMART/NVMe المتاحة عند طلب المستخدم، مع المعاملات والمخرجات والأخطاء؛ لا استعلامات إضافية تلقائية بعد فشل الطلب.
6. إتاحة التصوير الخام إلى وجهة يحددها المستخدم، مع المرور والنطاق والمحاولات ظاهرين وقابلين للضبط. لا يبدأ البرنامج تصويرًا أو يختار خطة إنقاذ بنفسه.
7. تغيير عامل واحد فقط عند تقييم مسار التوصيل، مع تسجيل النتيجة؛ لا تكرار دورات الطاقة تلقائيًا بلا حد.
8. عرض قيم السعة وأخطاء الوصول والفصل والمهل كما أبلغتها مصادرها، مع التاريخ والنطاق والمعاملات. يبقى قرار متابعة التجارب أو فحص العتاد أو إيقاف الجلسة للمستخدم.

تعرض الجلسة القراءات والسجلات والمقارنة الزمنية وملاحظات المستخدم. لا احتمالات أسباب، ولا درجات ثقة، ولا حكم صحة مولد من DRC، ولا خطوة مقترحة. توضع ملاحظات المستخدم في مساحة مستقلة موسومة بأنها من المستخدم.

## 6. البيانات المعروضة لكل جهاز

### الهوية والتوصيل

- الشركة والموديل والرقم التسلسلي وإصدار البرنامج الداخلي إن توفرت.
- معرف جلسة الاتصال ومسار النظام الحالي وهوية الوسيط؛ لا نعتبر diskN هوية دائمة.
- جهاز مادي، قسم، حاوية APFS، حجم، صورة قرص، أو جهاز افتراضي.
- داخلي/خارجي، وقرص نظام/بيانات، وSSD/HDD إن أمكن التحقق.
- المسار: منفذ ← موزع ← محول ← وسيط، مع VID/PID وهوية الجسر إن توفرت.
- التفريق بين USB/Thunderbolt كوسيلة توصيل، وNVMe/SATA كبروتوكول الوسيط، وUASP/BOT كمسار نقل USB؛ وجود USB-C لا يثبت Thunderbolt.

### السعة والبنية

- الحجم الدقيق بالبايت، وعرض GB/TB مع GiB/TiB عند الحاجة.
- حجم القطاع المنطقي والمادي، وعدد LBAs والمحاذاة إن كانت معلومة.
- GPT/MBR، بداية ونهاية وحجم كل قسم، والمساحات غير المخصصة.
- نظام الملفات، وUUID، وموضع التركيب، وحالته للقراءة/الكتابة.
- NTFS: بيانات boot sector وMFT/MFT mirror ومعرفات الملفات والأعلام وخصائص streams/ADS والضغط والملفات sparse وreparse points والأذونات وفق قدرة القارئ، مع الاحتفاظ بالحقول الأصلية غير المعروفة.
- FAT/exFAT: بنية الجداول والأدلة والـclusters والحقول التي يتيحها القارئ، مع عناوينها وقيمها الأصلية.
- APFS: الحاوية والمخازن المادية والأحجام والمساحات المشتركة؛ لا نجمع أحجام الحاوية بطريقة تضاعف السعة.
- حالة التشفير والقفل؛ النسخة الخام لا تفك التشفير ولا تستبدل كلمة السر أو المفتاح.

### الصحة والاستجابة

- SMART/NVMe health: الحرارة والإنذار الحرج وساعات التشغيل والقراءات/الكتابات والأخطاء والتآكل، بحسب ما يدعمه الجهاز.
- جدول الحقول كاملًا: ID/اسم الحقل، raw value، normalized/current/worst/threshold عند وجودها، الوحدات، flags، وسجلات الأخطاء والاختبارات التي يعرضها المصدر. فك ترميز bitmask يظهر مع القيمة hex/original، دون إسقاط vendor-specific أو unknown fields.
- تغير القيم بمرور الوقت إن كانت القراءة آمنة؛ لا polling متكرر تلقائيًا على القرص غير المستقر.
- زمن القراءة وتوزيع التأخير، والسرعة الفعلية، والمهل والفصل، ضمن نطاق العملية الجاري تنفيذها.
- خريطة: لم يُقرأ، قُرئ، يحتاج إعادة محاولة، غير مقروء؛ التأخير وحده لا يثبت تلف NAND.

### السرعة والطاقة

- ثلاث قيم منفصلة: السرعة المعلنة للوسيط، وسرعة الرابط التي يبلغها النظام، وسرعة النقل المقاسة أثناء عملية محددة.
- التيار الذي يعلنه الجهاز ومتطلبات الطاقة/إمكانات المنفذ إذا توفرت. لا نسميه «السحب الآن».
- قيم فعلية للأمبير والفولت والواط فقط عندما تأتي من جهاز قياس معروف؛ USB meter يقيس العلبة والقرص معًا، وليس كل خط داخلي على لوحة SSD.
- إضافة وحدة Telemetry لاحقًا لأجهزة قياس تقدم واجهة موثقة؛ تبقى البيانات منفصلة عن معلومات USB المعلنة.

مواصفات [USB Type-C](https://www.usb.org/sites/default/files/USB%20Type%20C%20Functional%20Test%20Specification%202021%2005%2020.pdf) تستخدم bMaxPower لوصف حد الاستهلاك المعلن. استنتاج التصميم: لا يجوز تحويله إلى قياس لحظي. جهاز القياس المختار يجب أن يحافظ على مسار البيانات والتوافق والسرعة اللازمة للتجربة.

كل قيمة تحمل المصدر ووقت الجمع وحالتها: متاحة، غير مدعومة، محجوبة من المحول، صلاحية ناقصة، فشل قراءة، أو قديمة بعد الفصل. لا تُستبدل القيم المفقودة بصفر.

هذه القائمة تنظيم أولي وليست حدًا للحقول: يحتفظ adapter بالحمولة الأصلية كاملة، ويتيح قسمًا لكل الحقول الإضافية وغير المعروفة. عند عدم ثبوت سبب غياب قيمة تعرض رسالة الأداة، ولا يخمن DRC أن المحول حجبها. الإحصاء الحسابي مثل معدل النقل أو عدد المهل يوسم بأنه محسوب مع وحدته وفترته ومدخلاته؛ لا يتحول إلى استنتاج عن سبب أو صحة.

## 7. workflows الأساسية

### تعريف سريع

قائمة الأجهزة وأحداث الاتصال، ثم التفاصيل عند الطلب. لا تركيب تلقائي من DRC ولا اختبار سطح أو اختبار ذاتي أو تحديث firmware. الفلاش الشخصي ينتهي نطاق استخدامه هنا.

### إنقاذ البيانات من مصدر غير مستقر

العمليات المتاحة: تحديد مصدر ووجهة، تصوير خام بخريطة استكمال، تحليل صورة، واستخراج ملفات. المستخدم يختار الترتيب والأداة والإعدادات؛ هذه ليست رحلة إجبارية أو خطة يقررها البرنامج. يبقى الالتزام بحماية المصدر وفحص صلاحية الوجهة شرط تنفيذ تقنيًا.

يدعم التصوير القرص كله أو قسمًا أو نطاقًا محددًا. البداية بلا محاولات متكررة كثيرة؛ إعادة قراءة المناطق الصعبة خطوة لاحقة يختارها المستخدم وفق النتائج. يعرض التقدم بالبايتات المقروءة والمفقودة والمناطق المؤجلة، ولا يعتبر الملف الكبير أو نجاح خروج العملية دليلًا على اكتمال الإنقاذ.

وفق [دليل GNU ddrescue](https://www.gnu.org/software/ddrescue/manual/ddrescue_manual.html)، خريطة mapfile أساس الاستكمال والعمل على نسخة أفضل من إصلاح المصدر. نستفيد من هذه القدرة ونبني حولها هوية المصدر والوجهة وحالة الجلسة.

### نسخ الملفات من نظام ملفات قابل للقراءة

متصفح ملفات على صورة أو مصدر ثبت تركيبه للقراءة فقط، واختيار ملفات/مجلدات، مع تقدم وأخطاء لكل ملف. دعم الأذونات والتواريخ والسمات وresource forks/ADS والروابط بحسب المصدر والوجهة. يوضح البرنامج فقدان معلومات لا يستطيع نظام الوجهة حفظها.

النسخ المنطقي ليس بديلًا مضمونًا عن التصوير على مصدر يفصل؛ قد يسبب قراءة متفرقة. توجد إمكانية مستقبلية لأولوية ملفات معينة عبر خريطة امتدادات تدعمها أداة ونظام ملفات مختبران، ولا يعد بها الإصدار الأول.

### فحص نطاقات القطاعات

اختيار البداية والطول بالبايت أو LBA، والمحاذاة إلى حجم القطاع، ومحدودية عدد المحاولات والسرعة. ليس هناك «فحص عميق تلقائي» عند التوصيل.

يفضل إعادة استخدام بيانات التصوير لعرض مناطق البطء والأخطاء بدل إعادة قراءة المصدر كله. الصورة مناسبة لتحليل البنية والأقسام، لكنها لا تكشف أداء العتاد الأصلي.

### استعادة الملفات من صورة

المستخدم يختار بين هذه الأدوات دون تبديل آلي بينها:

1. قراءة بنية نظام الملفات واستخراج الملفات مع الأسماء والمجلدات التي يتيحها القارئ.
2. البحث عن تواقيع الأقسام دون كتابتها للمصدر.
3. carving بالتواقيع حسب أنواع الملفات والإعدادات التي يحددها المستخدم.
4. عرض حجم الناتج والمناطق المتعذرة ورسائل التحقق التي أبلغتها الأداة. يربط فقدان القطاعات بامتدادات الملف عندما توفر الأداة خريطة موثوقة، ولا يضيف DRC حكمًا تخمينيًا عن تلف الملف.

[PhotoRec](https://www.cgsecurity.org/testdisk_doc/photorec.html) لا يعيد أسماء الملفات أو شجرة المجلدات الأصلية. [TestDisk](https://www.cgsecurity.org/wiki/TestDisk) يستطيع اكتشاف أقسام APFS، لكن قائمة وظائف نسخ/استرجاع الملفات لديه تختلف؛ لا نعامل اكتشاف القسم كدعم استعادة ملفات APFS كامل.

### الصيانة والكتابة

مراحل لاحقة: تهيئة نظامية، إنشاء/تعديل أقسام، إصلاح نظام الملفات، إعادة كتابة GPT/MBR، استرجاع جدول أقسام محفوظ، نسخ صورة إلى قرص، وكتابة نطاق خام بمصدر بيانات محدد.

كل عملية تعرض خطة فعلية وهوية القرص والنطاق والمخرجات المتوقعة، ثم تتطلب فتح الكتابة لهذا الهدف. وضع «force» لا يتجاوز حماية قرص النظام أو الفلاش الشخصي أو حدود الوسيط. لا يصلح مكونًا كهربائيًا أو متحكمًا متوقفًا، ولا يتجاوز بالضرورة read-only الذي فرضه المتحكم.

Sanitize/Secure Erase وTRIM/discard وتحديث firmware وإعدادات security أدوات منفصلة لاحقة، مشروطة بالدعم وفهم أثرها. كتابة أصفار على LBAs ليست دليلًا على محو كل NAND في SSD. لا حاجة لهذه العمليات لإنقاذ بيانات القرص الحالي.

## 8. الواجهة

قائمة أقراص دائمة، ومساحة تفاصيل كاملة في الوسط، وشريط حالة للمصدر والحماية، وطرفية يمكن إبقاؤها مفتوحة في الأسفل أو بجانب التفاصيل. الافتراضي مساحة عمل للمستخدم المحترف، لا ملخص يخفي التفاصيل أو wizard يفرض ترتيبًا.

تبويبات التفاصيل:

1. **الجهاز:** الهوية والبيانات المبلغ عنها وقدرات الأدوات وحالة الاتصال.
2. **الاتصال والطاقة:** المسار والبروتوكولات والسرعة المعلنة/المقاسة ومصدر قيمة الطاقة.
3. **الأقسام ونظام الملفات:** رسم أقسام ومعلومات دقيقة وتشفير وتركيب.
4. **SMART / NVMe والسجلات:** الحقول الأصلية كاملة وأعلامها والوحدات ومخرجات المصدر، مع قياسات الاستجابة.
5. **إنقاذ البيانات:** تصوير خام أو إخراج ملفات ومعاينة الوجهة.
6. **فحص النطاقات:** إعدادات قراءة واضحة وخريطة النتائج.
7. **الصيانة:** عمليات الكتابة تظهر مقفلة مع سبب القفل.
8. **العمليات والتقارير:** السجل والتقدم والاستكمال والمخرجات.

واجهة إنجليزية LTR بالكامل، وفق BRAND-SYSTEM.md في جذر المشروع: لوحة داكنة محايدة، حدود واضحة، monospace للقراءات، sans للعناوين والنصوص، ومفردات التخزين الفعلية. الوحدات بجانب القيم، والتفصيل قابل للتوسيع. اللون لا يكون الوسيلة الوحيدة للتعبير عن الحالة. دعم لوحة المفاتيح وقارئ الشاشة وكثافة معلومات قابلة للتغيير. تعليمات المستخدم حول عدم الاستنتاج وعدم اختزال القراءات تتقدم على الأمثلة العامة في ملف الهوية.

### عقد عرض المعلومات دون فقد

- جميع الحقول التي تعيدها الأداة متاحة في واجهة التفاصيل، وليست محصورة في الطرفية. دعم البحث والفرز واختيار الأعمدة وعرض البنية الشجرية حسب نوع البيانات.
- الاسم الأصلي والقيمة الخام بجوار التسمية الإنجليزية والقيمة المفكوكة الترميز. لا تحويل وحدات أو تقريب يستبدل الأصل؛ العدد الدقيق والصيغة الأصلية متاحان دائمًا.
- لا حذف للحقول غير المعروفة، ولا اختزال flags أو bitmasks أو سجلات الأخطاء إلى أيقونة لون. تحفظ الحمولة الأصلية كمرجع مستقل عن parser.
- التصفية والإخفاء اختيار صريح للمستخدم، مع بيان الفلتر وعدد السجلات المخفية وإمكانية إعادة العرض كله. عدم رسم جميع الصفوف دفعة واحدة لأسباب الأداء لا يعني إسقاطها من السجل.
- رسوم الأداء أدوات عرض إضافية؛ العينات الفعلية وتوقيتها والنطاق والمحاولات تبقى متاحة. إذا كانت الأداة لا توفر بيانات لكل قطاع لا يخترع DRC هذه الدقة.
- stdout وstderr وحالة الخروج والمعاملات والتوقيت وإصدار الأداة تحفظ كاملة، مع استثناء الأسرار المحددة في نموذج السلامة فقط. حد ذاكرة العرض لا يقطع ملف السجل الدائم بصمت.
- شاشة ضبط متقدمة للمعاملات المدعومة، ومعاينة الأمر قبل التنفيذ. أي معامل لا يدعمه adapter يظهر بوضوح؛ لا يستبدل أو يتجاهل بصمت.
- القوالب الاختيارية تعرض كل إعداداتها ويمكن تعديلها؛ لا طبقة تتنبأ بهدف المستخدم أو تختار إجراءً له. لا badges لدرجة صحة مولدة أو قسم احتمالات عطل أو إجراء موصى به تلقائيًا.
- حكم أبلغته الأداة مثل SMART PASSED يعرض موسومًا بمصدره، مع الحقول والسجلات كاملة؛ لا ينسب إلى DRC.

قبل التصوير يظهر المصدر والوجهة بوضوح، مع اتجاه النسخ، وسعة كل منهما، وهل الوجهة ملف أم قرص سيُستبدل محتواه. تحويل العملية من ملف إلى قرص لا يحدث تلقائيًا.

الطرفية في وضع الحماية تعرض الأمر والمخرجات الخام. إدخال المستخدم يمر عبر أوامر مدعومة ومصنفة في المحرك؛ لا نستخدم shell مفتوحًا ثم ندعي أنه read-only. إذا أضيف shell حر لاحقًا، يكون وضعًا مستقلًا يوقف ادعاء الحماية البرمجية للمصدر، ولا يعمل بصلاحيات helper المرتفعة.

## 9. التقنية المقترحة

| الجزء | الاختيار | السبب |
| --- | --- | --- |
| المحرك المشترك | Rust | نماذج صارمة للهوية والعمليات، إدارة عمليات طويلة، وربط بواجهات الأنظمة |
| إطار التطبيق | Tauri 2 | تطبيق مكتبي لثلاثة أنظمة وربط صريح بين الواجهة والمحرك |
| الواجهة | TypeScript + React | واجهة إنجليزية غنية بالمعلومات، LTR، ومكونات قابلة للاختبار |
| عرض المخرجات | xterm.js | عرض الطرفية الأصلي مع فصل المشاهدة عن صلاحية التنفيذ |
| سجل الحالات والعمليات | SQLite | معاملات وحفظ محلي لتقدم العمليات ونسخ المخطط |
| تبادل المعلومات | JSON/Plist ثم نموذج مشترك | تفضيل المخرجات المنظمة على تحليل النص البشري |
| جسر macOS محدود | Swift/Objective-C عند الحاجة | SMAppService وXPC وواجهات Apple؛ منطق السلامة يبقى في Rust |

هذا قرار هندسي للمشروع وليس ضمان موثوقية بسبب اللغة. موثوقية المنتج تعتمد على نموذج التفويض، والاختبارات، ومراجعة الأخطاء، وتوزيع أدوات موثوقة.

[Tauri](https://v2.tauri.app/security/) يفصل الواجهة عن Rust بصلاحيات IPC، لكن كود Rust نفسه يحتاج فرض سياساتنا. يمكن تضمين [برامج جانبية](https://v2.tauri.app/develop/sidecar/) منفصلة لكل نظام ومعمارية. تفاصيل الطرفية تتبع [إرشادات xterm.js](https://xtermjs.org/docs/guides/security/).

بدائل: SwiftUI ممتاز لواجهة Mac فقط لكنه يوسع إعادة العمل للأنظمة الأخرى. Qt خيار ناضج للواجهات المكتبية، لكن اختيار Rust/Tauri يلائم المحرك المقترح والواجهة المشتركة. لا حاجة إلى خدمة سحابية لتشغيل عمليات القرص.

## 10. الهيكلة

```text
واجهة React / Tauri
        ↓ طلب عملية معرف ومحدد المعاملات
خدمة التطبيق: الحالات والأجهزة والعمليات
        ↓ تخطيط وفحص السياسات والقدرات
محرك Rust مشترك
        ├── نموذج الجهاز والهوية والعلاقات
        ├── سياسة حماية المصدر والتفويض
        ├── مدير العمليات والاستكمال
        ├── محولات الأدوات وقراءة المخرجات
        ├── سجل SQLite وتقارير وخرائط قطاعات
        ├── FileSystemBackend: NTFS / FAT / exFAT / APFS / غيرها
        ├── VolumeLayoutBackend: GPT / MBR / حاويات متعددة الأجهزة
        ├── EncryptionBackend: فك قفل ببيانات المستخدم حيث يوجد دعم مختبر
        └── واجهة PlatformBackend
                ├── macOS: Disk Arbitration / IOKit / diskutil
                ├── Linux: udev / sysfs / أدوات النظام
                └── Windows: Storage APIs / SetupAPI / DeviceIoControl
        ↓ عمليات محدودة تحتاج امتيازًا
خدمة صغيرة خاصة بالنظام، مستقلة عن واجهة المستخدم
```

المحرك لا يعتمد على Tauri ليتم اختباره دون الواجهة. الوحدات الخاصة بالنظام لا تقرر واجهة المستخدم؛ تعيد بيانات وقدرات وحالات فشل محددة.

`PlatformBackend` يتيح الوصول للجهاز والامتيازات. `FileSystemBackend` يقرأ مصدر قطاعات أو صورة عبر واجهة موحدة؛ لا يفترض أن macOS يركب NTFS أو أن Windows يركب APFS. يمكن تغيير قارئ نظام الملفات دون تغيير UI أو مدير التصوير. طبقات التشفير والحاويات تقدم مصادر قراءة افتراضية عند دعمها، ولا تفسر على أنها قرص جديد صالح للكتابة تلقائيًا.

عقود أساسية:

- `DeviceIdentity`: معرف الوسيط وقرائن التحقق وهوية الاتصال الحالية، مع درجة قوة الهوية.
- `DeviceTopology`: علاقة الأقسام والحاويات والمخازن المادية ومسارات التوصيل.
- `CapabilitySet`: قدرات الوصول/التصوير مستقلة عن قدرات كل نظام ملفات وتشفير/حاوية؛ حالة كل قدرة وإصدار backend وسبب الرفض الموثق إن توفر.
- `OperationPlan`: المصدر والوجهة والنطاق والأثر والأداة وإصدارها والامتيازات اللازمة.
- `SafetyDecision`: سماح/رفض مع أسباب، وليس زرًا من الواجهة.
- `Job`: حالة التشغيل والإيقاف والاستكمال وهوية ملفات النتائج والخريطة.
- `Observation`: معرف الحقل واسمه الأصلي والقيمة الخام ووحدته وأعلامه ومصدره وتوقيته وحالة توافره؛ أي تحويل حسابي يحتفظ بالأصل.
- `RawArtifact`: حمولة الأداة الكاملة وصيغتها وstdout/stderr وحالة الخروج والمعاملات غير السرية وإصدارها؛ لا يسقطها parser عند عدم تعرفه على حقول.
- `FileSystemBackend`: عمليات منفصلة مثل probe وinspect وlist وextract وverify وrepair وformat، لكل واحدة قدرة معلنة. لا تعد كلمة «دعم NTFS» وحدها عقدًا كافيًا.

تصنيف كل عملية يفصل أربعة أمور: الكتابة للمصدر، والكتابة للوجهة، وتغيير حالة المتحكم، وشدة القراءة. عملية تقرأ فقط قد تضغط على قرص ضعيف، وعملية الاستعادة تحتاج كتابة إلى وجهة سليمة.

لا plugin عشوائيًا بصلاحيات root. نبدأ بمحولات داخلية مراجعة، مع API واضح لإضافة أدوات موثوقة لاحقًا.

## 11. الصلاحيات والتوزيع

واجهة التطبيق لا تعمل كـroot. على macOS نختبر helper صغيرًا موقّعًا مع [SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice) المتاح من macOS 13، وتواصل يتحقق من العميل. اعتماد التثبيت والخدمة وFull Disk Access حسب حاجة الأداة خطوات نظام واضحة، ولا نضع كلمة مرور المستخدم في السجل.

بداية الاستهداف macOS 13+ arm64، مع إثبات الاختبارات أولًا على البيئة الحالية. الإصدار القابل للتوزيع يحتاج توقيعًا وnotarization وتحققًا من أدواته ومراجعة آلية تحديثه؛ لا تعطيل SIP أو خفض أمن الإقلاع كخطوة افتراضية.

Homebrew مفيد لبيئة التطوير، لكنه لا يكون شرط المستخدم النهائي. لا تنفذ خدمة مرتفعة برنامجًا من مسار يستطيع المستخدم تغييره. أدوات التوزيع مثبتة الإصدار ومعروفة المصدر ومتحقق منها، مع وثائق تراخيصها والمصدر المطلوب عند إعادة التوزيع. فصل البرامج إلى processes لا يلغي التزامات التراخيص.

Windows: helper وصلاحياته واكتشاف الأجهزة خاص بالنظام؛ GNU ddrescue ليس وعدًا بنسخة Windows مكافئة. وثيقته تحذر من أخطاء Cygwin المضللة. نبدأ بدعم تعريف الأقراص وتحليل الصور، ولا نعلن دعم التصوير الخام على Windows قبل اختبار backend معتمد.

## 12. حفظ الحالات والنتائج

لكل حالة مجلد على وسيط سليم يحتوي: تعريف المصدر، وسجل الأحداث، وخطة العملية، وإصدار الأدوات، والصورة، وmapfile، وبصمة تحقق للصورة، وتقرير النتائج.

SQLite يحتفظ بفهرس الحالة والعمليات، لكنه لا يحل محل mapfile ولا يكتب ملفات الحالة على المصدر. تعتمد صلاحياته على المستخدم الحالي، وتكون الملفات الحساسة محلية. السجل يتجنب الأسرار، مع اختيار إخفاء الأرقام التسلسلية والمسارات عند التصدير.

البصمة تثبت حالة ملف الصورة وقت حسابها، ولا تثبت اكتمال استعادة المصدر. نحسبها من الصورة؛ لا نقرأ المصدر المريض بالكامل مرة أخرى افتراضيًا من أجل التحقق. صورة ناقصة يجب أن تظل موصوفة بأنها ناقصة مع خريطة المناطق غير المستعادة.

## 13. مراحل التنفيذ ومعايير الخروج

### المرحلة 0: إثبات الجدوى والسلامة

- تثبيت عقود الهوية والسياسة والقدرات قبل الواجهة النهائية.
- إثبات فصل وصول macOS عن قارئات NTFS/exFAT/FAT، وتصوير مصدر ذي نظام ملفات مجهول دون محاولة تركيبه.
- استخدام ملفات صور تجريبية وقرص اختبار مخصص للعمليات الخطرة؛ ليس الفلاش الشخصي.
- إثبات مراقبة الاتصال وحماية مسار التنفيذ ومنع اختيار وجهة على نفس المصدر.
- اختبار حد API وصلاحيات helper وعدم قدرة الواجهة على تمرير أمر اعتباطي.
- بوابة خروج: اختبارات حماية المصدر والهوية والوجهة ناجحة، وحدود macOS موثقة.

### المرحلة 1: تعريف الأقراص وواجهة المعلومات

- قائمة الأجهزة وتحديث أحداث ظهورها واختفائها.
- الهوية والتوصيل والسعة والأقسام وحالة التركيب، مع قدرات ومصادر البيانات.
- SMART قراءة معلومات فقط عندما يدعم المسار ذلك، لا تحفيز اختبارات ذاتية.
- سجل خام وتقرير محلي.
- الفلاش الشخصي يستخدم هنا فقط؛ عند أول اتصال يحتاج المستخدم تحديد الجهاز المقصود ثم تثبيت سياسته. لا استنتاج من الاسم وحده.
- عرض الجداول والسجلات الأصلية كاملة، مع حقول إضافية/غير معروفة وبحث وفلاتر معلنة؛ لا استنتاجات أو توصيات عمليات.
- بوابة خروج: تمثل الواجهة NTFS/exFAT/FAT والأقسام والمعلومات المفقودة والتشفير والجسور وAPFS حيث يدعمها المصدر، وتحافظ على قيد الفلاش ولا تفقد حقول الأدوات.

### المرحلة 2: إنقاذ خام قابل للاعتماد

**أولوية معتمدة من المستخدم — 14 أكتوبر 2026:** تصوير القرص هو الهدف الحالي. نوقف التوسع في تحليل الصور واستخراجها وفي ميزات الصيانة حتى تقوية مسار التصوير للحالات غير المستقرة. الميزات الموجودة تبقى متاحة. «مهما كان القرص عنيدًا» ليست ضمانًا تقنيًا: لا يمكن تصوير قطاعات لا يتيحها الجهاز، أو استحداث البيانات التي لم ترجعها القراءة.

بوابة الجاهزية الإضافية:

- وصول خام بصلاحيات قراءة محددة عبر helper؛ لا رفع كامل الواجهة ولا تغيير أذونات أجهزة المستخدم.
- تجهيز حماية التركيب قبل التوصيل، مع إظهار حدودها؛ الحارس الحالي يبدأ عند إعداد العملية ولا يغطي التوصيل الأول أو إعادة الترقيم تلقائيًا.
- إعادة ربط صريحة بعد الفصل أو تغير diskN/المنفذ، مع مقارنة هوية المصدر وسعته وحجم القطاع وحفظ تاريخ النقل؛ لا يعتمد التطابق على الاسم والحجم فقط.
- تعامل واضح مع الإيقاف المتأخر والقراءة المحجوزة في النواة، وحفظ الخريطة الحالية والنسخة الاحتياطية والأحداث والأجزاء المسترجعة. مهلة ddrescue ليست ضمانًا لمهلة نواة النظام.
- استكمال النطاقات في الصورة والخريطة نفسيهما، مع معاينة المراحل والاتجاه وحدود القراءة وإعدادات التوقف؛ لا إنشاء صور متفرقة لمجرد تغيير النطاق.
- فشل الوجهة أو امتلاؤها أو تعذر حفظ الخريطة يوقف الاعتماد على الحالة القديمة؛ لا تعني سعة الملف أو صفر bad-sector أن التصوير مكتمل.
- اختبار EIO ثابت ومتنقل، انقطاع المصدر وإعادة ترقيمه، مهلة القراءة، تعطل التطبيق/الوجهة، وخريطة مفقودة أو مبتورة أو قديمة، وتقدم ملفات العملية بعد آخر حفظ للجلسة. تستخدم محاكاة وملفات مخصصة ثم قرص اختبار مخصص عند توفره؛ لا فحص بيانات الفلاش الشخصي.
- إتمام النطاق يتطلب خريطة نهائية جديدة صالحة، وهوية الوجهة الأصلية وحجمها الصحيح وخروج الأداة بنجاح. وصف تصوير كامل للمصدر يتطلب أيضًا نطاقًا يغطي كامل السعة المعتمدة؛ لا يمثل ذلك حكمًا على سلامة البيانات الداخلية أو إمكانية فك التشفير.


- دمج GNU ddrescue على macOS إلى ملف صورة أولًا؛ يشمل أقراص ويندوز ومصادر مجهولة نظام الملفات ومشفرة كقطاعات خام.
- اختيار مصدر/وجهة، وفحص المساحة ونظام الوجهة، واستكمال مضبوط بالهوية والخريطة.
- حفظ تقدم وإيقاف واستعادة بعد انهيار البرنامج أو امتلاء الوجهة.
- عرض خريطة القراءة، والسرعة، والمناطق المؤجلة وغير المقروءة.
- مصدر غير مستقر: عملية قراءة واحدة في الوقت نفسه، ومهل وسياسة توقف محدودة.
- بوابة خروج: سيناريوهات الفصل وإعادة الترقيم والوجهة الممتلئة لا تسبب قراءة/كتابة للجهاز الخطأ أو خسارة حالة الاستكمال.

هذه أول نسخة مفيدة مباشرة للـSSD الحالي إن ظل يقدم قطاعات قابلة للقراءة. لا ننتظر وظائف التهيئة حتى نستفيد من الاستعادة.

### المرحلة 3: استخراج الملفات وتحليل الصور

- تركيب الصور للقراءة فقط حيث يسمح النظام، ومتصفح واستخراج ملفات.
- Sleuth Kit وPhotoRec وتحليل أقسام TestDisk، بمحولات مثبتة الإصدار.
- NTFS/exFAT/FAT ضمن أول حزمة استخراج على الماك، مع corpus يشمل metadata والأسماء وADS وحالات التلف؛ تختبر الأنظمة الأخرى وAPFS حسب قدراتها دون ربط الدعم بنظام المضيف.
- التشفير والحاويات لها مصفوفة مستقلة: التعرف أو التصوير لا يعلن دعم فك القفل أو استعادة ملفات غير مختبر.
- تقارير نتائج الأداة والقطاعات الناقصة والملفات المستخرجة، دون حكم جودة تخميني من DRC.
- بوابة خروج: استخراج صور أقراص ويندوز من تطبيق يعمل على macOS، وعدم تعديل الأصل، وتوثيق حدود كل قدرة على حدة.

### المرحلة 4: الصيانة والكتابة

- فتح كتابة لعملية محددة على هدف محدد، وإعادة قفل بعد انتهائها أو الفصل.
- نسخ صورة إلى قرص، وتهيئة وأقسام، وإصلاح نسخة عمل، ثم كتابة نطاقات خام.
- لا unlock للفلاش الشخصي ضمن النطاق الحالي، ولا كتابات إلى قرص النظام.
- بوابة خروج: جميع سيناريوهات الكتابة اختبرت على صور وأقراص اختبار مخصصة؛ لا اعتماد على «force» لمعالجة هوية غامضة.

### المرحلة 5: الأنظمة الأخرى والتوسع

- Linux: اكتشاف وSMART وتصوير ثم nvme-cli وقدرات منخفضة المستوى حسب الجهاز.
- Windows: اكتشاف وتحليل صور، ثم backend تصوير مثبت الاختبارات، ثم كتابة مقيّدة.
- قياس طاقة خارجي، E01/libewf، ووحدات ملفات/تشفير/حاويات إضافية، وتكامل أدوات قياس وتحكم متقدمة وتصدير إلى أدوات تجارية يختارها المستخدم.
- لا تعلن قدرة في الواجهة قبل قياسها واختبارها على النظام ومسار التوصيل المعني.

لا توجد مدة زمنية موثوقة قبل إثبات الجدوى على أجهزة حقيقية؛ مراحل الخروج هي مقياس التقدم.

### متطلب تجربة الاستخدام المعتمد: الوضع السهل ثم توثيق الاستخدام

تحديث 14 أكتوبر 2026: طلب المستخدم تقديم وضع **Easy** الآن بجانب **Professional**، مع دعم لينكس وتشيت شيت وتوثيق تثبيت ديبيان. هذا الطلب يقدّم هذه الأعمال على الترتيب السابق؛ وضع Easy في 0.4.0 يحافظ على نفس الجلسة والقراءات الخام وقواعد حماية المصدر.

- الوضع السهل يكفي لاستخدامات الفحص والاستعادة المعتادة: اختيار المصدر والوجهة، عرض القراءات، استخراج الملفات، التصوير الخام مع التقدم والإيقاف والاستكمال، والعمليات المناسبة للقدرات المكتملة.
- يخفي الإعدادات المتقدمة من المسار الرئيسي ويتيح الرجوع إلى الوضع الاحترافي؛ لا يحذف بيانات المصدر أو الحقول الأصلية أو سجلات الأوامر، ولا يستنتج تشخيصًا أو يختار عملية بدل المستخدم.
- القراءة فقط وقيد الفلاش الشخصي وفحوص هوية المصدر والوجهة تتطابق في الوضعين. العمليات التي تتطلب تمكين الكتابة تظل صريحة ومحددة بالهدف.
- يختبر المساران على السيناريوهات المعتادة، ثم يكتب توثيق الاستخدام للوظائف المثبتة فقط.

الرسوم تعرض قياسات مصدرها معروف ووحدتها ظاهرة؛ غياب العينة يظهر كفجوة ولا يتحول إلى صفر. السرعة والمتوسط من سجل ddrescue مفصولان حسب المحاولة، والمدة الزمنية للأمر موسومة كمدة عملية كاملة، وتوزيع الأقسام يستند إلى السعات المبلغ عنها. لا تستحدث هذه الرسوم قراءة تلقائية من القرص أو اختبار سرعة إضافيًا.

## 14. خطة التحقق من الموثوقية

- parsers أمام مخرجات صحيحة ومفقودة ومبتورة وميزات غير مدعومة؛ SMART exit status يعالج كأعلام متعددة، وليس فشلًا واحدًا.
- تطابق كل حقل وقيمة في الحمولة الأصلية مع ما يمكن الوصول إليه في الواجهة والتصدير؛ بما فيه vendor-specific وunknown fields والأرقام الكبيرة والأعلام وسجلات الأخطاء.
- لا ملخص صحة أو أسباب عطل أو درجة ثقة أو اختيار عملية يصدر عن DRC؛ حالات الأداة موسومة بمصدرها، والتصفية اختيار معلن للمستخدم.
- NTFS/exFAT/FAT على macOS، وأنظمة أخرى عبر قارئاتها، وحالات نظام مجهول أو تشفير؛ التصوير الخام لا يعتمد على نجاح probe أو mount.
- hot-plug وتبدل diskN وغياب serial وتطابق الأسماء والأحجام.
- مصدر ووجهة يشتركان في القرص المادي، حتى عبر أقسام أو APFS أو روابط المسارات.
- قراءة فقط وتفويض helper ومحاولات تمرير أوامر إضافية وأسماء ملفات غير مأمونة.
- قراءة متوقفة/مهلة/فصل وبيانات فشل محقونة، والتأكد من أنه لا يوجد retry loop غير محدود.
- إنهاء العملية وإعادة فتح الحالة بعد إيقاف التطبيق أو فقد الطاقة، وحفظ mapfile وسجل متسق.
- امتلاء الوجهة، وقيود FAT32 وأحجام الملفات، وفشل حفظ الخريطة قبل تلف حالة الاستكمال.
- أحجام قطاعات 512/4096، ومحاذاة النطاقات، وحدود حسابية وحفظ الأرقام الكبيرة دون فقد دقة JavaScript.
- مقارنة بصمات مصادر اختبار قبل وبعد عمليات القراءة، وقياس الأوامر عند ادعاء حماية مادية؛ لا نفحص مصدر SSD المريض مرتين افتراضيًا لهذا الغرض.
- اختبارات الكتابة على صور وأقراص مخصصة فقط، مع فصل تام عن جهاز المستخدم الشخصي.

قائمة معايير السلامة التنفيذية في [نموذج السلامة](SAFETY_MODEL.ar.md)، ومصفوفة القدرات في [ترسانة الأدوات](TOOL_MATRIX.ar.md).


### نطاق 0.4.0: Easy ولينكس والمرجع

- Easy يعرض ملاحظات القرص والسعة الدقيقة وSMART والحرارة عندما تُطلب وتُبلغ عنها الأداة، مع خطوات صريحة للفحص والتصوير واستعراض الصور. لا ينتج تشخيصًا أو تقييمًا للصحة.
- مرجع الأوامر داخل النافذة، ماك ولينكس مع ملفات تثبيت Debian / Ubuntu / Mint، بحث بالأعلام، وأمثلة للنسخ فقط؛ عمليات الكتابة المرجعية مخفية افتراضيًا. Windows والعائلات الأخرى لاحقًا.
- خلفية Linux تستعمل lsblk / udev / sysfs وتحتفظ بمخرجات الأوامر الخام. قبول ملفات الصور والوجهات يحتاج حل كل الأقراص الفعلية في سلسلة التخزين.
- التصوير الفيزيائي في Linux يقبل قرصًا فعليًا ثانويًا، بما فيه SATA/NVMe الداخلي، بعد إثبات أنه لا يخدم النظام أو swap وأنه غير مركب، ويحتاج مقبض قراءة حصريًا. عند رفض الوصول المباشر يُطلب OpenDevice بوضع r فقط من UDisks2 مع تفويض النظام، ولا يُشغّل البرنامج نفسه كجذر. الحجز اختُبر على loop مخصص؛ التفويض والقرص الفيزيائي يحتاجان تحققًا مستقلًا. الفلاش الشخصي محمي، والقرص المتعطل غير متاح.
- حزم .deb لمعمارَي AMD64 وARM64 تُبنى في Debian 12، وتضم GNU ddrescue 1.30 ومكتبات قارئ الصور الخاصة. نشر نسخة على GitHub مشروط بنجاح البناء والاختبارات.
